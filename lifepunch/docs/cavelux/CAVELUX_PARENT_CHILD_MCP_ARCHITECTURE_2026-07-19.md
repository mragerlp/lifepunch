# CAVELUX PARENT / CLIENT-CHILD MCP ARCHITECTURE (2026-07-19)

Owner-articulated + ratified. THIS is the structural move that makes Cavelux a COMPANY (repeatable product) instead of a one-off rig. The parent MCP is the product/moat; each client MCP is a repeatable engagement stacked on it.

## THE LAYERING
PPP LLC
  └── CAVELUX MCP (PARENT) = the METHOD, universal, the PRODUCT + moat
        ├── governance enforcement (default-deny · least-privilege · evidence · human-canon)
        ├── two-lane mount system (big crate / lean mount)
        ├── the eye (web-render — every client reads references)
        ├── Context7 (live docs — universal)
        ├── body/inference layer (Blackbox gateway, swappable harnesses)
        ├── workflow primitives (Superpowers/TRIP — method, not domain)
        └── brain-feed pattern (read A tree/board/doctrine — generic mechanism)
        │
        ├── LIFEPUNCH MCP (CHILD) = domain layer, FIRST CLIENT, live proving ground
        │     ├── s&box competence (sboxclaude toolsets, API schema, roslyn, slang)
        │     ├── LIFEPUNCH tree/doctrine/board as Resources
        │     ├── DXRP portal reader
        │     └── LIFEPUNCH-specific lanes + dispatches
        │
        └── [FUTURE CLIENT MCP] = their domain (their docs/tools/engine), stacked on the SAME parent

## THE PRODUCTIZATION LOGIC
- CAVELUX MCP (parent) = the REUSABLE IP. Build once = the moat, the "governed software operating system." Knows NOTHING about s&box/LIFEPUNCH — it's the method that molds to ANY operation.
- Each CLIENT MCP (child) = a REPEATABLE ENGAGEMENT. Stack the client's domain on the parent — faster each time because the hard universal part is done. Law firm -> Cavelux parent + their-docs child. Game studio -> Cavelux parent + their-engine child.
- LIFEPUNCH = the FIRST child = live proving ground (exactly the CVL-site pitch: "method builds AI capability around real operations").
- Parent = the product; child = the engagement.

## MAPS TO OWNERSHIP HIERARCHY (same shape = it's right)
PPP LLC -> Cavelux (method/apparatus) -> LIFEPUNCH (first purpose). Parent MCP = Cavelux; child MCP = LIFEPUNCH. Corporate structure and technical architecture are the SAME shape.

## BUILD IMPLICATION (critical — build parent-first, not retrofit)
Build the MCP AS A PARENT from the start. The universal layer (governance, mount, eye, Context7, bodies, workflows) is Cavelux; the s&box/LIFEPUNCH layer is a CHILD that calls up to the parent + adds domain tools on top. Do NOT build a monolith and split later.

## TECH DECISION AT THE PARENT/CHILD SEAM (Phase-B, build-seat decides)
MCP-calling-MCP (child->parent) is doable; concrete shape = either (a) child COMPOSES/PROXIES parent's tools, or (b) both mounted to the same client, child DEPENDS ON parent's presence. This is where the earlier SWALLOW fork (bundle/proxy vs manifest/orchestrate) gets ANSWERED. Not a blocker; the build seat rules it.
